## 2. 支持的数据库(第一版)

按**数据模型**分两类 —— 这决定了数据视图组件要不要分派。

### 关系型(行式表格视图)

| 引擎 | 对象树层级 | 选它的理由 |
|---|---|---|
| PostgreSQL | 连接 → database → schema → table/view/func/seq | 最主流,功能最全(schema/分区/扩展) |
| MySQL / MariaDB | 连接 → database → table/view/proc | 装机量最大 |
| SQLite | 连接 → database → table | 零配置本地文件,开发者日常高频 |
| SQL Server | 连接 → database → schema → table | 企业刚需,Windows 生态为主 |

### NoSQL(各自的专属视图)

| 引擎 | 数据模型 | 数据视图 |
|---|---|---|
| MongoDB | 文档 | **文档树**(BSON 嵌套展开) + JSON 切换 |
| Redis | KV | **键列表**(key/type/TTL/size) + 按类型渲染的值编辑器 |

### 二期候选

ClickHouse(OLAP 列存,对象模型同 PG,成本低)、Elasticsearch(搜索)、Oracle(企业但驱动重)、云 KV(DynamoDB / Atlas)

## 3. 各引擎的对象树不统一 —— 保留原生层级

| 引擎 | 层级数 | 有无 schema | 特有对象 |
|---|---|---|---|
| PostgreSQL | 3 | 有 | 扩展、分区、序列、类型 |
| MySQL | 2 | 无(库=schema) | 存储过程、函数、事件、触发器 |
| SQLite | 1–2 | 无(`main` 为隐式 schema) | 索引、视图、触发器 |
| SQL Server | 3 | 有 | 存储过程、聚合函数、同义词 |
| MongoDB | 2 | 无 | 集合、视图、索引 |
| Redis | 2 | 无(db0–db15 编号库) | 按类型分组 + TTL |

**设计取舍:保留引擎原生层级,不做跨引擎压平。**

```text
▾ PostgreSQL — 本地
  ▾ postgres                     ← database
    ▾ public                     ← schema
      ▸ users         1,284
      ▸ orders        5,321
▾ MySQL — 本地
  ▾ shop                         ← database
    ▸ users         1,284
▾ Redis — 本地
  ▾ db0                          ← 编号库
    ▸ String          6,201
    ▸ Hash              890
```

理由:

1. **PG 的 database 是可 CREATE/DROP 的独立实体**,压平等于让 PG 支持不完整。DBeaver / pgAdmin / Navicat 的 PG 都是 database → schema → table 三层全显。
2. **「各引擎深度不一」对树组件不是问题** —— TreeView 本来就是任意深度的递归结构。
3. **差异由配置驱动,不进组件代码**:每个引擎提供一份树规格(有哪些分组项、有哪些对象类型、是否懒加载),TreeView 组件保持通用,不做 `if engine == PostgreSQL` 这类分支。

实现约定:引擎树规格是一份纯数据(`{ groups: [...], objects: [...] }`),Rust 侧对应 `seladb-core` 的驱动能力声明;两侧共用同一份语义,避免设计源与实现分叉。

## 4. 信息架构

采用 Navicat / DBeaver / TablePlus 的共识:**对象树做主导航,Tab 做工作区**。

```text
┌─ 标题栏 ─────────────────────────────────────────────────────┐
│ SelaDB │ ⌘K 搜索                    │ ☀ 🌙 ⚙ │ [+ 新建连接]  │
├─ 工具栏 ─────────────────────────────────────────────────────┤
│ [刷新][打开查询] │ [提交 ▾][回滚] │ 事务 Auto │ MySQL—本地 ▾ │
├────────────┬──────────────────────────────────────────────────┤
│ 对象树      │ Tabs: [MySQL] users │ [PG] public.orders │ +   │
│ ┌────────┐ │ ┌──────────────────────────────────────────────┐ │
│ │🔍 搜索 │ │ │ 过滤条: [id > 100        ]  清除              │ │
│ └────────┘ │ ├──────┬──────────┬──────────┬──────────────┤ │
│ ▾ MySQL    │ │ #    │ id       │ name     │ created_at   │ │
│  ▾ shop    │ │  1   │ 1001     │ 伟        │ 2025-03-28   │ │
│   ▸ users  │ │  2   │ 1002     │ 娜        │ 2025-05-11   │ │
│   ▸ orders │ │  …   │          │           │              │ │
│ ▾ Postgres │ ├──────┴──────────┴──────────┴──────────────┤ │
│  ▾ postgres│ │ 筛选:[__________]        1,284 行   导出 ▾   │ │
│   ▾ public │ └──────────────────────────────────────────────┘ │
│    ▸ users │                                                 │
├────────────┴──────────────────────────────────────────────────┤
│ ● 已连接 127.0.0.1:3306 │ 1,284 行 │ 12ms │ UTF-8 │ 事务 Auto│
└─────────────────────────────────────────────────────────────┘
```

要点:

- **全局工作区**:多个连接可同时打开,对象树顶部列出所有连接,各自可展开
- **单栏对象树**,宽度可拖拽(用 `Splitter`)
  - 拖拽手柄是一条几乎看不见的窄缝,中间放一个**竖向三点握把**;
    反馈只落在握把上 —— 悬停时整条线变色会让人以为那儿是一条可点的线,而不是一个把手
  - 握把周围扩一块透明热区,4px 的窄缝本身太难点
- **Tab 不绑定连接**,标题带引擎+连接标识(如 `[MySQL] users`),跨连接对比直接开两个 Tab
- **工具栏按「连接级 / 数据级」分区**;提交/回滚只作用于**当前 Tab 所属连接**,这个归属必须在 UI 上明示
- 工作区 Tab 可拖拽排序、标脏、关闭前确认
- 状态栏固定显示:连接状态 / 行数 / 耗时 / 字符集 / 事务模式

### 数据视图要抽象成接口

NoSQL 和关系型的数据视图结构完全不同,所以不能都塞进 `DataGrid`:

```js
interface DataView {
  mount(container)
  destroy()
}
```

由 `TableDataView` / `DocumentDataView` / `KeyValueListView` 分别实现。`DataGrid` 只是 `TableDataView` 的内部实现。

### 数据网格:纯原生自研

不用 AG Grid / TanStack Table。理由是**设计源要能复刻**:引入第三方表格库,设计源就会长成那个库的样子,Rust 实现阶段就变成在复刻 AG Grid 而不是复刻我们自己的设计;headless 库(TanStack)则只省逻辑不省外观,视觉仍要全手写,却多引入构建步骤与包体。

代价要如实记:光虚拟滚动核心约 150 行,加上列宽拖拽、排序、筛选、单元格编辑、列显隐、右键菜单,整张表在 **500–700 行**量级。

## 7. 设计系统

### 视觉语言参考

配色与形态参考本机的 **MCode**(一个 Electron 桌面应用)。色值直接从它的
截���上采样,不是凭感觉调的:

| 用途 | 深色 | 浅色 |
|---|---|---|
| 内容区 | `rgb(28,28,28)` | `#ffffff` |
| 侧栏 | `rgb(23,23,23)` | `#f6f6f7` |
| 浮层卡片 | `rgb(38,38,38)` | `#ffffff` |
| 主文字 | `rgb(237,237,237)` | `#1c1c1e` |
| 次文字 | `rgb(148,148,148)` | `#6e6e73` |
| 更淡 | `rgb(102,102,102)` | `#a1a1a6` |
| 主色 | `rgb(2,119,217)` | `rgb(2,119,217)` |

三条要记住的规则:

1. **中性灰打底,只带一丝察觉不到的冷调**。之前用带蓝的灰做背景,整个界面泛冷蓝,
   像网页后台;但纯 R=G=B 的死灰在浅色端又显脏。带 3~4 级冷调(面板 `#f6f8fa`
   的 B 比 R 高 4)是这两头之间的落点 —— VS Code 2026 的 `#FAFAFD` 与 Radix
   gray-2 的 `#F9FAFB` 都落在这个位置。
2. **外壳是面板色,面板与画布之间用一条结构线分界**。
   - 外壳(顶栏 / 状态栏 / 左侧对象树)= `--bg-panel`,工作区画布 = `--bg-canvas`
   - **侧栏与主内容之间画 1px `--border-subtle` 竖线**;主内容内部不用线
   - 顶栏、Tab 栏、面板头、表格区属于主内容,彼此之间不用分割线
   - **外壳是「左右两大块」:左边是通高的对象树,右边自己再分上下。**

     ```
     ┌────────┬─────────────────────────┐
     │ 品牌   │ 顶栏                      │
     │ 搜索   ├─────────────────────────┤
     │ 对象树 │ 主内容(画布)              │
     │        ├─────────────────────────┤
     │        │ 底栏                      │
     └────────┴─────────────────────────┘
     ```

     顶栏与底栏**只覆盖右侧主内容区**,不横跨对象树 —— 对象树从窗口
     顶部一直到底,读起来才是一根完整的柱子,而不是被顶栏切了一截。
     这跟 DataGrip / DBeaver / Beekeeper / TablePlus 的结构一致
     (VS Code 例外:它的标题栏与状态栏仍是全宽,侧栏从标题栏下面开始)。

     品牌标识因此搬到侧栏顶部 —— 侧栏通高之后,窗口左上角就是侧栏的
     顶部,桌面应用的品牌该在这儿。品牌行高度跟顶栏一致(`--h-topbar`),
     于是侧栏的搜索框那一行跟右侧画布的顶边正好对齐。

     早先的版本是「上下三段,顶栏底栏横跨全宽」,侧栏被顶栏压在下面;
     更早还试过「顶栏底栏各压一条横贯全宽的浅灰线」,那条线会把侧栏
     从中间切断。三版都不如现在这一版:左边一整条,右边自己分上下。
   - **画布那三条边各有一条 1px 结构线**:上、下画在 `.workspace` 的
     border 上(它就是画布容器),左边画在 `.tree` 的 border-right 上。
     三条边同一个 token(`--border-subtle`),画布于是成了一张嵌在灰框里的纸。
     参照实现给的是同一套:VS Code 2026 的 `titleBar.border` /
     `statusBar.border` 都是 `#F0F1F2` 这一档的细边,`surface.border`
     是 `#E4E5E6`(我们的 `--border-subtle` 就在这一档)。

   **为什么是「淡底 + 1px 线」而不是「一整片深灰」**:侧栏原来是 `#f3f3f4`、
   画布 `#ffffff`,靠 12 级底色差分界。那点差在 96% 亮度附近根本推不出
   边界 —— 侧栏与内容区之间是一条没有形状的过渡,整片灰又重又糊。
   拿到实测值对比:VS Code 2026 Light 侧栏 `#FAFAFD`(比画布只暗 5 级)、
   Light Modern `#F8F8F8`、ADS `#F8F8F8`、Beekeeper(Radix gray-2)
   `#F9FAFB`、Primer `#F6F8FA` —— **没有一个大厂工具用「一整片中灰 + 无边框」
   这个组合**,全部是「淡底 + 1px 边线」。现在取 `#f6f8fa`,配 `#e4e8ec` 的竖线。
3. **浮层是卡片:无边框 + 四周阴影**。菜单、对话框、命令面板、Toast、抽屉、
   快速开始的卡片一律 `border: none`,靠 `--card-shadow` 撑出边界,12–16px 圆角。

   关键在 **Y 偏移必须是 0**。带 Y 偏移的阴影只往下投,卡片看着像贴在底上
   而不是浮着:

   ```css
   --card-shadow:
     0 0 0 1px rgba(0, 0, 0, 0.05),    /* 零模糊 1px 细影,画边缘不是边框 */
     0 0 16px -2px rgba(0, 0, 0, 0.16),  /* 四周对称的柔光 */
     0 0 4px rgba(0, 0, 0, 0.05);
   ```

### 控件与行的形

规范是「区域靠底色分层,控件靠形状与状态分层」。落到具体控件上有几条:

- **输入位 = 白底 + 1px 边**(`--bg-input` + `--border-default`),不用「凹槽」。
  原来是「无边框的凹槽」—— 底色比所在区域深一档,聚焦时抬起来变白。
  这条在浅色端**不成立**:侧栏底色一抬到 `#f6f8fa`,凹槽比面板只深十几个色阶,
  人眼根本判读不出来,那块灰只是糊在面板上的一个色斑,不是「能输入的字段」。
  而白底 + 1px 边是 VS Code 2026(`input.background: #FFFFFF` + `input.border`)、
  macOS、Primer 的共同做法:深浅两端都不靠底色差撑着,靠的是「比周围亮 + 有边」。
  顶栏与侧栏两个搜索框统一走 `--bg-input`,聚焦是 accent 边框 + `--accent-soft` 光晕,
  跟 `.input` / `.select` 一套语言。
- **行的 hover / 选中 = 内缩的圆角块**,不是通栏的直角条。通栏元素的两端圆角
  悬在面板边缘像被裁掉的卡片,直角又跟整套圆角语言打架。内缩之后它跟计数
  徽标的胶囊、搜索框的圆角是同一套语言。
- **顶栏的分组靠间距读,不靠线**。组与组 8px,分隔线两侧各 2px(加上间距
  是 10px),按钮在组内 4px。之前组与组也是 4px,顶栏右段(提交/回滚 ·
  Auto · 当前连接 · 搜索框 · 图标 · 设置)一路 4px 挤到底,密到读不出
  分组 —— 顶栏是要放很多控件的地方,间距就是分组本身。
- **侧栏默认 296px,树行 29px**。左列要放得下「连接 → 库 → schema → 表 →
  计数徽标」四五级缩进,宽度不够就只能截断;296px 是 DataGrip / DBeaver
  的量级。
- **计数徽标 = 淡底胶囊**;行被 hover / 选中时,徽标去掉自己的底色 ——
  否则是灰底块里再套一个灰底胶囊,两层灰色叠在一起像打了补丁。
- **顶栏操作按钮一律 Ghost**(无边框,hover 才浮起)。桌面工具的操作条不该是
  一排带描边的大圆角网页按钮。`提交` 这种不可逆操作给一层额外权重:
  深色文字 + 强调色图标。
- **顶栏的「当前连接」是上下文指示器,不是动作按钮**。Ghost 化之后它跟
  「提交/回滚」长得完全一样,层级就丢了 —— 给它一块微底色药丸
  (`--bg-selected`,跟对象树里选中行同色),并且带上引擎图标,
  跟对象树里的连接节点呼应。

> **一条容易踩的坑:CSS 变体类必须比基础类更靠后,或更高特异性。**
> `.btn--tool` 曾经定义在 `.btn` 之前,同特异性下后者把前者整个盖掉,
> 于是顶栏所有按钮都渲染成带描边的实心按钮,而「Ghost 样式」的注释
> 一直写在旁边。**意图写在注释里 ≠ 样式生效。** 改完这类东西要用计算样式
> 核一遍,别只看截图。

### 顶栏

控件不能堆。左半边放数据级操作(刷新、查询),右半边放事务作用域
(提交、回滚、Auto、当前连接)与全局动作(搜索、主题、新建、设置),
中间用弹性空白推开。密度切换挪到设置页 —— 顶栏本来就有八个控件。

### 主题

三态:**浅色 / 深色 / 跟随系统**。默认跟随系统。

- 顶栏的主题按钮点开直接选三项(带勾选标记),不用循环切换去猜
- 顶栏有明确的「设置」入口,设置页里也能改
- 偏好持久化在 `localStorage`

`ui/assets/tokens.css` 是唯一设计源,双主题 + 双密度:

```css
/* 浅色 */
--bg-canvas:#ffffff; --bg-panel:#f6f8fa; --bg-surface:#f1f3f5;
--bg-raised:#ffffff; --bg-input:#ffffff; --bg-inset:#e9edf1;
--bg-selected:#e2e6eb; --border-subtle:#e4e8ec; --border-default:#d9d9dd;
/* 深色 */
--bg-canvas:#1c1c1c; --bg-panel:#151515; --bg-surface:#151515;
--bg-raised:#262626; --bg-input:#242424; --bg-inset:#202020;
--bg-selected:#2c2c2c; --border-subtle:#2a2a2a; --border-default:#303030;
/* 密度 */
--row-h:26px/32px; --row-h-tree:24px/27px; --fs-base:13px/14px;
```

背景这五个角色的分工别混:`canvas` 是工作区、`panel` 是外壳(顶栏/状态栏/对象树)、
`surface` 是次级面(输入框/查询区/子标签)、`inset` 是内嵌块(行号槽/主键行)、
`input` 是工具条里的输入位(白底带边框,比所在面板亮)。

**默认跟随系统主题。** 实现方式:JS 读 `matchMedia('(prefers-color-scheme: dark)')`,把结果写回 `<body data-theme>`,用户可在设置里显式覆盖为 light / dark / system。

- 与 VS Code / Zed / GitHub Desktop / JetBrains 新版一致,用户不用表态
- 实现成本几乎为零 —— 现有 token 结构本就是两套 `data-theme` 变量
- 截图回归测试时显式把主题钉死,即可拿到确定性基准
- Rust 实现侧走同一条链路,不会出现设计源与实现主题策略分叉

### 类型色板(数据网格专用)

| 类型 | 样式 |
|---|---|
| 整数 / 浮点 | 蓝色 |
| 字符串 | 常规前景色 |
| 布尔 | 强调色 |
| 时间 | 紫色 + 等宽 |
| **NULL** | 灰色斜体 |
| BLOB / JSON | 等宽 + 截断提示 |
| 主键 | 加粗 |

**密度可调是数据库工具的刚需** —— 同样 1000 行,紧凑模式能多看一半。

### 引擎图标

六种引擎各一枚专属图标,统一 **24×24 视窗、20×20 光学尺寸、单色 `currentColor`**,
颜色由容器的 `--engine-*` token 决定,深浅主题各自取色。

| 引擎 | 形状 | 来源 | 关键处理 |
|---|---|---|---|
| PostgreSQL | 象头 | 官方标志 | 白色路径用 `fill-rule="evenodd"` 挖成真负形 —— 那就是眼睛 |
| MySQL | 海豚 | 自绘 | 照官方跃起侧视:左上尖喙、弓形身段、左下 V 双尖背鳍、右下分叉尾 |
| SQLite | 羽毛 | 自绘 | 官方羽毛斜置 45°,16px 下只剩一笔;改成竖直,中脉做中段平行的宽缝 |
| MongoDB | 叶 | devicon,MIT | 去掉一条 0.2×0.6 的孤立噪点路径(16px 下是脏点);横向放宽 |
| Redis | 层叠立方 | 官方标志 | 三层各拉 22 单位,让 16px 下层间凹槽不被抗锯齿填死 |
| SQL Server | S | 自绘 | 官方 2025 图标压单色后笔画几乎铺满、内折口闭合;改画几何 S,开口做宽、整体收窄 |

四条硬规矩:

1. **负形必须按 16px 栅格设计,不能靠缩放。**
   大图里 1–2px 的缝缩到 16px 只剩 0.2–0.3px,抗锯齿后直接粘连成实心块。
   24 视窗到 16px 是 2/3 比例,所以**负形宽度要 ≥ 2.25 视窗单位**,才留得下 1.5px 的透明缝。
   SQLite 的中脉、MongoDB 的叶脉、SQL Server 的 S 内折口都是照这个数定的。
   这是这一轮改动最大的一条 —— 之前的版本就是靠缩放做的,于是 PostgreSQL 成了没五官的团块、
   Redis 成了实心六边形、SQL Server 的 S 糊成了 C。
2. **用实心剪影,不用线稿。** 线稿在 15px 下会糊成一团,官方品牌图形里 MySQL 海豚、
   MongoDB 叶、SQL Server 都是线稿,直接拿来用等于没有图标。
3. **形状按小尺寸重新裁剪,不照搬官方成品。** 官方 SQLite 标志是「深蓝方块 + 浅蓝羽毛」
   两层,压成单色只剩一个方块;官方 MySQL 海豚 48px 应用图标的素材是 GPL,不能直接用。
   官方 MySQL 海豚是 45° 斜置的**线稿**,照着它做实心剪影出来的是一根弯棍子;
   把身体改成官方那种**弓形**、背鳍放回**左下**(跃起的海豚是背对观众的)、头部挑出尖喙,
   才认得出是海豚。
4. **图标是实心的,颜色由 token 给。** 官方品牌色在深色主题下大多太暗
   (SQLite `#003b57` 在 `#151515` 上几乎看不见),所以一律用 `--engine-*`。

**辨识度按「误读」比按「看不清」更致命。** MySQL 一度画成水平的实心海豚并加了个圆眼睛,
结果整枚读成「卡通小金鱼」—— 头部太圆、眼睛太大。去掉眼睛、改回官方那种弓形跃起姿态、
把喙挑出来,才回到海豚。同理 MongoDB 试过左右两片叶,评审判它
「像裂开的咖啡豆 / 竖瞳」。**被认成另一种东西,比认不出更糟。**

**品牌语义优先于负形一致性。** 试过把 MongoDB 画成官方那种左右两片叶,16px 下确实能数出两瓣,
但视觉评审两轮都判它「像裂开的咖啡豆 / 竖瞳」,脱离品牌特征 —— 最后退回官方那片饱满的水滴叶,
接受它的细叶脉在 16px 下糊掉。**形状不像那个数据库,比看不清更糟。**

**海豚这类有机形态,靠描边几何拼不出轮廓。** 中间试过三条路:① 照官方 45° 斜置画实心剪影 →
一根弯棍子;② 官方线稿路径加 `stroke` 胀粗 → 胀出来的是「粗线海豚」,中间还是空的,
16px 下照样糊(线稿的内轮廓永远是空的,加粗描边填不满);③ 水平实心 → 读成小金鱼。
最后一条路才成立:**用官方的姿态骨架 + 官方的比例关系,自己重画成实心**。

**验收方法:像素栅格,不是看图。** 把图标真的渲染成 16×16 位图,逐像素打成 ASCII 网格
(`#` 有墨 / `.` 透明),负形留没留下是白纸黑字的。这套方法直接抓出了三个靠肉眼看不出的问题:
MongoDB 叶脉缝整个消失、Redis 层间凹槽糊死、SQL Server 的 S 骨架断裂。
评审则负责 48px 以上的观感与品牌语义 —— 两者互补,不能只靠其中之一。

**用在哪:** 对象树连接节点、Tab 引擎标识、面板标题徽标、引擎徽标、连接向导的引擎卡片、
DDL 预览的方言标识。**不用在哪:** 对象类型(表/视图/索引)继续用描边图标,两套语言分工 ——
实心彩色 = 引擎身份,中性描边 = 对象类型。

图标的唯一信息源是 `assets/engine-icons.js`;Rust 实现侧按同一套规格复刻。
**Rust 侧特别注意:** 归一化用的是 `getBBox()`,而 `getBBox()` 会忽略元素**自身**的
`transform` —— 任何「先缩放/旋转再量尺寸」的步骤,都必须把变换挂到子元素上量父级,
否则量到的是变换前的框,图标会超框。

### 视觉评审

功能断言验不了「好不好看」。`ui/tests/review.mjs` 把黄金截图交给多模态模型,
按固定 rubric 打分,输出可定位的问题清单。

思路借自 [wandb/openui](https://github.com/wandb/openui) 的
`backend/openui/eval/evaluate.py` —— 它用 GPT-4-vision 给生成的 UI 按三条
1–5 分:媒体质量 / 对比度 / 相关性。这里把三条改写成适配桌面数据工具的版本:

| 维度 | openui 原版 | SelaDB 版 |
|---|---|---|
| Media Quality | 桌面与移动端渲染 | **布局与信息密度** —— 专业工具的紧凑与层级,不是响应式 |
| Contrast | 明暗模式表现 | **对比度与类型可辨识** —— 类型色板彼此分不分得开 |
| Relevance | 是否满足需求 | **专业观感** —— 像商业数据库工具还是通用后台模板 |

命令:

```bash
cd ui && node tests/review.mjs              # 全部截图
cd ui && node tests/review.mjs 02-grid      # 只评某几张
cd ui && node tests/review.mjs --compare    # 改动前后成对比较
```

报告落在 `ui/tests/review-report.md`,成对比较的报告在 `ui/tests/compare-report.md`。

### 绝对打分不可靠,成对比较才靠谱

实测同一批截图连续评四轮,总分在 **8.07 / 8.73 / 8.80 / 8.33** 之间浮动 ——
多模态模型每个维度有 ±1 分的抖动,总分能差 1.5 分。绝对分数只能当方向,
不能当指标。

所以工具里另有一套成对比较:把改动前后的两张图一起给模型,问「哪个更好」。
相对判断稳定得多。基线截图放在 `ui/tests/baseline/`,更新基线的命令:

```bash
git show <基线commit>:ui/tests/screenshots/02-grid.png > ui/tests/baseline/02-grid.png
```

### 这一轮的实际数字

| 轮次 | 布局 | 对比 | 专业 | 合计 |
|---|---|---|---|---|
| 原始 | 2.93 | 2.53 | 2.60 | 8.07 |
| 第 1 轮(外壳密度与信息层级) | 3.13 | 2.87 | 2.80 | 8.73 |
| 第 2 轮(语义修正) | 2.87 | 2.93 | 2.87 | 8.80 |
| 第 3 轮(数值对齐与表头分层) | 2.80 | 2.80 | 2.80 | 8.33 |

后三轮在噪声范围内浮动,看不出趋势 —— 这正是绝对分数不可信的证据。
改用成对比较(基线 = 改造前),最终 **11/13 张判定改后更好**(另 2 张因
临时 OSS 上传失败未评)。

**评审的真正价值不是分数,是它指出的具体问题。** 每一轮改动都是从报告里
「被反复提到的问题」和「修改建议」里挑出来做的 —— 数值列右对齐、表头分两行、
UUID 降权、文档树紧凑化、顶栏按引擎显隐事务按钮,都是这么来的。

### 评审暴露过的几类真问题

这些都不是「审美偏好」,是能一眼验出来的东西:

| 问题 | 为什么是真问题 |
|---|---|
| 数值列左对齐 | 桌面数据工具的硬规矩,左对齐没法按位数比对金额 |
| 表头把列名和类型挤在一行 | 横向扫表扫不出字段名 |
| `--type-float` 与 `--type-uuid` 是同一个色值 | 两种类型在网格里完全分不开 |
| 过滤条出现在结构视图与 DDL 里 | 那两个是只读上下文,没有数据可过滤 |
| 查询写 GROUP BY,结果摊开整张明细表 | 设计源这么画,Rust 侧就会照着错 |
| 刷新与回滚用同一个图标 | 两个动作分不清 |
| 表头两行时第二行被压到数据行上 | 行高继承正文的 1.5,直接溢出 |

**教训:设计源的错误会被实现照抄。** 视觉上的小毛病到了 Rust 侧就不是小毛病了。

### 评审的意见要逐条用像素核实,误判要驳回

侧栏底色那一轮(2026-10-22)的教训。成对比较连着判了 4 张,3 张说「改前更好」,
理由听起来还很具体:

- 「新建连接卡片的描述文字出现字符重叠」
- 「改动后列宽被过度压缩,balance 与 is_active 表头标签重叠」
- 「顶部栏 Auto 控件丢失了背景容器」
- 「侧栏搜索框几乎与深色背景融为一体」

**逐条核实下来,四条全是幻觉:**

| 评审说的 | 实际 |
|---|---|
| 卡片文字重叠 | 该区域**像素 0% 变化**,卡片根本没被碰过 |
| 列宽被压缩、表头重叠 | 表格数据行与表头**各 0.00% 变化** |
| Auto 控件丢了背景 | 它本来就是 Ghost(`background: rgba(0,0,0,0)`),我没碰过 `.btn.btn--tool`;那 97% 的像素变化是**顶栏自身底色**改了 |
| 搜索框融进背景 | 深色下搜索框从 rgb(18,18,18) 变成 rgb(36,36,36),面板是 21 —— 从**比面板暗 3 级(隐形)**变成**比面板亮 15 级(清晰)** |

根因不在模型,在**工具**:拼接图把 1440px 截图塞进 790px 的栏里,缩到 55%,
1px 的结构分隔线被缩成半像素后抗锯齿掉 —— 模型看不见那条线,只看到
「灰色块变少了」,于是判成「容器感变弱、界面单薄」。把拼接图改成
「上半全景 + 下半 2 倍放大的角落」之后,同一批截图的结论直接翻转:
深色那张从「改前更好」变成「改后更好」,并且第一次说出了准确的理由
(「补充了明确的圆角边框与容器底色,显著提升了表单组件的交互感知」)。

**规矩:**
1. 评审说「引入了新问题」时,先问「这块区域像素变了吗」。用逐像素 diff
   分区统计(表格区 / 卡片区 / 侧栏区),变了几个百分点一目了然。
2. 评审说的每个「现象」都要落到计算样式或具体色值上,落不上就驳回。
3. **评审的价值是它指出的具体问题,不是结论。** 这次它唯一说对的一条
   (「搜索框右边缘离分割线过近,右侧留白偏小」)是真问题 —— 把侧栏搜索框
   右边距从 4px 放到 8px 就解决了。

### 评审工具要带差异掩码,不然它连「改了哪儿」都读不出来

顶栏/底栏加分割线那一轮(2026-10-22)又踩了一次同样的坑,但这次症状不同。

改了之后评审判了 2/4「改后更好」,两条负面理由全是**方向反了**的:

- 「改动前在顶栏下方保留了清晰的 1px 结构分隔线……改动后移除了这些关键分界线」
  —— 实际是改**前**没有线、改**后**才加上的(y=44 那一行:改前直接从
  顶栏色跳到画布色,改后多出一条 rgb(42,42,42))
- 「改动后与改动前在视觉呈现上完全一致,未能明确指认出任何有效的界面调整」
  —— 实际那一页整体 9.17% 的像素变了

根因还是工具:这次不是「线被缩没」,而是**改动太轻** —— 只多了两条 1px 线
加一次整体 1px 位移,模型光看两张并排的图分不清哪边是哪边,更读不出
「哪儿变了」。

**修法:给拼接图加一行逐像素差异掩码**(品红 = 改过的像素,灰 = 没变)。
这是客观事实,模型拿它当锚点,判断就落得到具体位置上。加上掩码后,
同一批截图的结论从 2/4 变成 **4/4 判改后更好**。

但**方向对了不等于理由可信** —— 加了掩码之后模型仍然会编细节,说
「键名搜索框右侧增加了精确匹配模式下拉框」「微调了行高与垂直内边距」
「居中排版修正」,而 `assets/` 里根本没有「精确」这个东西。
所以规矩不变:**结论看方向,理由逐条核实,一条都不能直接采信。**

**借的是它的 eval 思路,不是它的产物。** openui 生成的是 Tailwind + shadcn 的
React 代码,直接拿来会同时违反「零第三方 UI 依赖」「零构建步骤」「tokens.css
唯一真源」三条约束,而且审美会变成通用 shadcn 味。

三条需要 Rust 实现侧对齐的约定:

1. **SQL 语法色板**在 `tokens.css` 的 `--syntax-*`。Rust 侧用 `tree-sitter-sql`
   做词法分析,但**配色以设计源为准**。
2. **行数口径**:设计源每张表只手写十几行 mock,按确定性规则扩到 600 行,
   底栏显示「1,284 行 · 已加载 600」。真实实现里这个数字来自分页状态。
3. **查询 Tab 只对关系型引擎开放**。Redis 是 KV,没有 SQL 查询编辑器,
   将来给它做的是命令控制台,不是同一个组件。

## 9. 已拍板决策

2026-10-22 评审确认,五条全部定案:

| # | 议题 | 结论 |
|---|---|---|
| 1 | 第一版引擎清单 | **6 个全上**:PostgreSQL / MySQL / SQLite / SQL Server / MongoDB / Redis |
| 2 | 数据网格实现 | **纯原生自研**,零第三方表格依赖,视觉全由 `tokens.css` 控制 |
| 3 | 默认主题 | **跟随系统**,设置里可显式覆盖 |
| 4 | 多连接模型 | **全局工作区 + Tab 带连接标识**,对象树顶部并列所有已打开连接 |
| 5 | 对象树层级 | **保留引擎原生层级**,差异由每个引擎的树配置驱动,不进组件代码 |

第 5 条是对初版方案的修正:初版曾提议「跨引擎压平成两层分组」,核对 DBeaver / pgAdmin / Navicat 的实际做法后推翻 —— PG 的 database 是可 CREATE/DROP 的独立实体,压掉它等于让 PG 支持不完整;而「各引擎深度不一」对任意深度的树组件本就不是问题。

## 10. 设计源与 Rust 实现的职责边界

`ui/` 已经 1 万行上下。再往下走,它很容易从「设计基线」变成「平行实现」——
HTML 版把每个交互都做全,Rust 侧等于照着它重写一遍,两边迟早分叉,
而且分叉之后没人知道哪边是对的。

所以在这里把边界钉死。

### 设计源负责

| 类别 | 具体内容 |
|---|---|
| **视觉 token** | 颜色、间距、字号、圆角、阴影、动效 —— `tokens.css` 是唯一真源 |
| **布局度量** | 固定高度、栅格、缩进、层级行的视觉节奏 |
| **交互模型** | 有哪些状态、状态怎么流转、什么动作触发什么反馈 |
| **信息架构** | 对象树结构、Tab 组织方式、面板与抽屉的职责边界 |
| **配色语义** | 类型色板、引擎色、SQL 语法色、状态色 |

### 设计源不负责

- **功能完备性**。设计源里的按钮可能是空动作,边界情况可能没覆盖。
  这些在 Rust 实现时按真实数据补齐,不用回头改设计源。
- **真实数据**。全部是 mock。mock 的行数、类型分布只要「像真的」就够。
- **性能**。虚拟滚动在设计源里是为 600 行做的,真实实现面对的是十万行。
- **并发与错误处理**。设计源里所有操作都是同步的。

### Rust 实现侧对齐清单

| 设计源 | Rust 侧 | 对齐标准 |
|---|---|---|
| `tokens.css` | `seladb-gui` 的主题模块 | token 命名与取值一一对应;**不允许组件里写裸色值** |
| 数据类型色板 | 驱动的类型分类 | 分类规则一致(见 `datagrid.js` 的 `TYPE_CLASS`) |
| SQL 语法色板 | `tree-sitter-sql` | **配色以设计源为准**,词法分析以 tree-sitter 为准 |
| 引擎树规格 | `seladb-core` 的驱动能力声明 | 同一份语义,避免设计源与实现对同一引擎的理解分叉 |
| 布局度量 | 固定高度常量 | 数值逐项对应,允许平台微调 |
| 交互模型 | 事件与状态机 | 状态集合与流转路径一致,实现可以更严谨 |

### 判断标准

改 Rust 实现时,**该不该回头改设计源**?

- 改的是**看起来什么样** → 改设计源,截图基线跟着更新。
- 改的是**行为细节或边界情况** → 只改 Rust 实现,设计源不动。
- 改的是**交互模型本身**(多了一个状态、流程变了) → 两边都改。

判断不清的时候,先假设是第二种 —— 设计源是基线,不是需求文档。

### 关于 `DiffViewer`

P1 里唯一没做的组件。它要做的是「两个表结构的差异对比」,但这依赖真实的
schema 版本历史,设计源里造不出有说服力的样例。硬造一份会让基线失真,
所以留着不做 —— 等 Rust 侧有真实的历史数据了再补,那时补的是实现而不是设计。
