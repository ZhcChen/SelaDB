# ADR-0003：核心库与引擎、UI 双解耦，三种外壳平权

- 状态：已采纳
- 日期：2026-10-21

## 背景

产品形态有三个：交互式 CLI、GUI 桌面客户端、供 AI Agent 使用的 MCP Server。用户明确提出「CLI 很重要，同时可以封装 MCP 或 skill；GUI 是客户端实现」。这意味着三者不是主次关系，而是同一能力的不同投射。

风险在于：如果业务逻辑散落在 CLI 命令或 GUI 绑定里，第二个外壳开工时就会发现要重写一遍，第三个（Skill）更无从谈起。

## 决策

**引入 `seladb-core/src/service` 用例编排层，作为业务逻辑的唯一落点。** 三种外壳都只做三件事：解析参数 → 调用 service 方法 → 格式化输出。

- `seladb-core/src/core` 定义领域模型（连接、库、schema、表、列、结果集）
- `seladb-core/src/driver` 定义引擎无关的抽象，由各引擎模块实现
- `seladb-core/src/service` 编排核心能力，**不感知具体外壳，也不感知具体引擎**
- CLI / GUI / MCP 分别作为 service 的消费者存在

配套约束：

- 领域类型（列类型、结果集）在驱动边界完成映射，上层不做引擎特定的类型断言
- CLI 的所有命令必须提供 `--json` 输出，这是 Skill、MCP、CI 三条路径的共同基础
- Skill 不直接调用 Go API，而是包装 CLI 的 JSON 输出（见 `docs/architecture.md` 第 5 节）

## 理由

- **避免重复实现**。MCP 工具与 CLI 子命令几乎同构，一份 service 实现同时喂饱三条路径
- **行为一致性可验证**。CLI 和 MCP 输出结构相同，测试可以共用夹具
- **为未来留门**。要加第 4 种外壳（比如 VS Code 插件、JetBrains 插件）时只需再写一层适配

## 后果

- 多了一层间接。`service` 不是无意义的透传，它承担了「跨引擎的语义统一」职责（比如把各引擎的 schema 概念差异抹平），这层有实际价值
- service 的方法签名需要显式携带 `connID` 而非绑定连接对象，这让它天然可被 MCP 这类无状态调用方使用
- 代价：service 层定稿后，新增外壳的边际成本才真正降下来。在此之前，抽象有可能过早
