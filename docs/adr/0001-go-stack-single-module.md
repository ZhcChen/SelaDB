# ADR-0001：全栈 Go，单 module 多 package

- 状态：已采纳
- 日期：2026-10-21

## 背景

项目定位为跨平台数据库管理软件，CLI、GUI、MCP Server 三种形态均要实现。初期曾考虑把「多模块」实现为 monorepo 内多个 `go.mod`（用 `go.work` 聚合），以便核心库、驱动集、CLI 各自独立发版。

## 决策

**全项目使用 Go 语言**（GUI 前端除外，见 ADR-0004）。仓库采用**单 `go.mod` + 多 package** 结构，通过包路径划分职责，而非拆分成多个 module。

## 理由

多 `go.mod` 的成本在项目初期是明确且立即发生的：

- CI 需要为每个 module 独立解析版本号与 tag
- `go.work` 与 CI 的模块解析容易不一致，交叉编译时 `GOWORK` 行为需要额外调试
- 依赖升级要逐 module 执行并处理版本冲突
- 本地开发需要额外的 `go work` 维护动作

而收益（独立发版、依赖隔离）在当前阶段一个都用不上：项目尚无第三方消费者，也没有需要隔离的依赖版本冲突。

拆分的真实触发条件是明确的，等到出现再拆成本很低：

1. `pkg/seladb` 需要被其他项目依赖并独立发版
2. 某个驱动需要支持与其余部分不同的依赖版本
3. 需要发布独立的驱动 SDK 供第三方实现自定义引擎

## 后果

- 单一版本号，发布简单
- 跨包重构自由，无需协调多 module 的版本
- 代价：一旦对外发布 `pkg/seladb`，`internal/` 与 `pkg/` 的边界会变成事实上的兼容契约，需要靠 ADR 和 code review 约束
