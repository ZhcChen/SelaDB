SelaDB GUI 架构 HTML / CSS / JS 作为源语言 → 编译成 Rust

0一句话与两个硬约束

SelaDB 的界面用 HTML / CSS / JS 写，编译成 Rust。 发布产物是纯 Rust 原生应用（无 JS 引擎、无 HTML 解析器、无 DOM）； 开发期有一个 Rust 写的解释器做即时预览。

发布产物里没有 JS 引擎
逻辑层必须能 AOT 到 Rust
来自「最终编译都是翻译成 Rust」
开发期要即时反馈
必须有解释器，且要与 AOT 产出一致
来自「主要还是开发运行时」

为什么是 HTML/CSS/JS，不是自研 DSL

  • AI 时代的第一论据 —— 全世界 AI 训练数据里前端代码都是 HTML/CSS/JS。界面语言是 HTML/CSS 时 AI 零学习成本；换成自研 Rust DSL，它得学一套世界上没有先例的 API。
  • 照抄语义比自己发明便宜一个数量级 —— DOM 语义、flexbox、 grid、级联、事件、焦点序、无障碍，全是全世界被验证过几万遍的东西。

设计源的角色变了

  • 那 8362 行 JS 不是 mock，是逻辑层的浏览器版。它在浏览器里 需要假后端，于是有 mock-data.js；SelaDB 里假后端换成 Rust 对象，JS 一行不改。
  • 所以设计源从此不只是「视觉基线」，而是逻辑层的可运行参考实现： 浏览器里双击即开，Rust 引擎里跑真后端，同一份 JS。

2IR：三个部分

节点模板

「HTML 的结构」，不是运行时的活树。没有计算样式、没有几何、 没有事件监听。拆开的好处：模板可序列化（编译期产物）、可对比 （一致性测试）、可被 codegen 遍历。

样式表

规则表 + 变量表（233 个 token）+ 主题层（data-theme / data-density）。 「不支持」要报错，不能忽略 —— 解析遇到不认识的东西 → 记进 unsupported → 编译失败。

宿主绑定

「Rust 给 JS 的那个对象」的接口面。 不是凭空设计的 —— 是被设计源已经定义好的（见 §3）。

3「对象」：唯一的宿主收口

设计源在浏览器里跑的时候，逻辑层调的是 mock-data.js + mock-sql.js 里的全局。 实测：mock 层定义 31 个顶层名字，逻辑层实际只用到 10 个。

组 名字 Rust 侧对应 状态
数据CONNECTIONSlist_databases / 连接配置已实现
TABLE_DATA查询结果已实现
TABLE_STRUCTUREdescribe_table已实现
DOCUMENTSMongoDB 文档未做
KEYSRedis 键未做
ENGINESEngine 枚举已实现
UI_COPY文案表未做

其余 21 个是 mock 的内部辅助（SQL 分词、DDL 拼装、类型推断）， 逻辑层一次都不碰，Rust 侧也不用做。
所以「换后端就是换实现，调用点一行不改」—— 这是这套架构最省事的地方。

名字必须逐字一致

JS 侧是全局（设计源不能用 ES module，file:// 下 CORS 会拦），所以宿主以 SELADB 注入全局作用域， 能力名与 mock 层逐字一致。

SELADB.TABLE_DATA —— 浏览器里由 mock 提供， SelaDB 里由 Rust 对象提供，同一个名字。

FFI / JNI 的收口

Rust 侧可以把「调用其他语言（FFI / JNI）」的能力挂到这个对象上， 而核心仍由 Rust 提供。落法：对象持有一张不透明句柄表， JS 侧 SELADB.foreign.invoke(handle, "method", args)， 实际的外语调用由 Rust 执行。

好处：跨语言调用有唯一收口，可审计、可限制、可回溯。

4实测：JS → Rust 这条路，语言层面可行

四个「无底洞」全是 0

生成器 / yield0不用处理协程状态机
Proxy / Reflect0不用做元编程
Symbol0不用做属性键类型系统
eval / new Function0不用做动态编译
另外三个决定性的简化：
· ES module 语法 0 处、跨文件重名 0 个 → per-file 翻译成立，不需要链接器
· await 5 处、async 4 处、Promise 1 处 → 不必翻 async runtime
· 正则 99 条，lookaround / 反向引用 / 命名组 全是 0 → 可直译到 Rust regex crate

真正要设计的只有 3 处

闭包捕获可变外层变量69要 &mut 生命周期
标签模板40要转 Rust 宏
类字段 this.x =177要 &mut self

其余是机械改写：++/-- 2041 处、 this. 753 处、私有字段 # 234 处。

局部 let 只占 18%（47 顶层 vs 57 全部）→ 闭包捕获可变状态的面很窄，69 处可控。

CSS 子集（同样实测）

508 条声明组 / 528 条选择器。子代 >、通用兄弟 ~、:not()、:nth-child()、 ID 选择器、!important、calc()、 @media / @supports / @layer / @container / @import / @font-face 全是 0。

所以「照抄 CSS」不是「实现 Blink」，是「实现一个 CSS 子集引擎」。

5虚拟化：节点不是数据的唯一通路

这是数据网格不炸内存的唯一办法，浏览器也是这么做的（它也不把行 放进 DOM）。设计源自己的数据网格早就是虚拟化的：rowPool 复用 DOM 行，只渲染「视口内 + 上下各 10 行余量」—— 它早就承认了「DOM 行不是数据通路」。

结构节点

  • 进节点树 ✓
  • 参与布局 ✓
  • 绘制：递归画子节点

虚拟化表节点

  • 进节点树 ✗（只存一个描述）
  • 参与布局 ✓（占位 + 滚动条）
  • 绘制：引擎直接画行，不经过节点树
关键点：虚拟化在引擎层，不在组件层。 逻辑层只声明「这是一张 N 行的表 + 列定义 + 排序状态」， 行池、定位、绘制全在引擎。组件不是「自己实现虚拟化」。
10 万行 × 10 列 = 100 万节点，每个几百字节 —— 直接爆内存。

6一致性与风险

一致性契约 —— 本项目最关键的测试设施

同一批 HTML/CSS/JS 输入，解释执行的结果与 AOT 产物的结果必须逐像素相同。

需要三样东西共用：同一套 IR、同一套宿主 API 面（§3 的 10 个名字）、 同一套样式匹配 / 布局 / 绘制实现（都在 gui-core）。

代价要说清楚：JS 语义要在两处实现（解释器的引擎 + AOT 编译器）。 这是本架构最容易被低估的成本。缓解办法是子集足够小， 且两条路径共享绝大部分。

#风险等级缓解
R1 JS 语义双实现不一致（解释器 vs AOT） 高 对拍是硬门禁；子集小
R2 闭包可变捕获在 Rust 里表达不了 高 M4 先验证；必要时限制子集
R3 自研 JS 解析器工作量大 中 用 swc 系（Apache-2.0），不自研解析器
R4 总产能（框架已估 8–18 个月，加上工具链与开发套件） 高 里程碑切小；每步都有可运行产物
R5 cssparser 的 MPL-2.0 不在白名单 中 待拍板（taffy 的 parse feature 已依赖它）
R6 开发期运行时的成本被低估 中 开发期可用现成引擎，一致性靠对拍

7里程碑与待拍板

里程碑

M0gui-core 能编译
M1gui-ir + gui-parse（HTML/CSS）
M2布局 + 绘制，一个静态页面上屏
M3gui-interp，解释执行 JS 逻辑层
M4gui-codegen，翻一个真类（TreeView）
M5宿主对象 SELADB，10 个能力接上
M6虚拟化表，10 万行不爆内存
M7一致性对拍，逐像素相同
M8完整应用跑起来

M4 是风险点：第一个真类，闭包可变捕获（69 处）的问题会在这里 第一次暴露。

待拍板

D3JS 解析器用 swc 还是自研差一个数量级
D4开发期运行时用现成引擎还是自研差一个数量级
D5HTML 结构翻成 Rust 代码还是编译成二进制与「都是 Rust」有张力
D6cssparser 的 MPL-2.0 白名单硬阻塞

D6 是唯一硬阻塞 —— taffy 的 parse feature 已经依赖 cssparser，不解决，gui-parse 的 CSS 解析器就没法开工。
